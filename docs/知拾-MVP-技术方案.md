# 知拾 MVP 技术方案

**版本：v0.1｜日期：2026-09-19｜需求基线：[PRD v0.2](./知拾-MVP-PRD.md)**

状态：技术实施基线。Electron 技术路线已获用户确认；本文描述拟实施方案，不表示桌面程序、十类多主题分类及正式引注已经实现。本次交付为文档及项目目录整理，不实施资料格式迁移、不调用用户模型 API。

## 1. 目标与关键决策

构建 Windows 优先、单人使用、本地优先的文献阅读与笔记桌面程序。完成“收录—解析—阅读笔记—摘要分类—证据问答—导出”闭环，落实 PRD 的 A01–A21 验收要求。

| 决策 | 选型与范围 | 理由 |
| --- | --- | --- |
| 桌面应用 | Electron；首发 Windows 11 x64，后续评估 macOS | 利用网页界面能力与本地文件能力；复用现有前端技术 |
| 界面 | React + TypeScript + Vite，沿用现有 Tailwind CSS | 以组件方式组织目录、阅读器、笔记和问答，减少重写 |
| 文献引擎 | Python 3.12 系列 + FastAPI + Pydantic | 复用现有解析、校验、检索和模型服务 |
| PDF 阅读 | PDF.js，固定匹配的库与 worker 版本 | 原页显示与证据定位共用页面坐标体系 |
| 永久资料 | 原件 + JSON/YAML/Markdown 开放文件 | 延续仓库现有 Canonical File Store，便于迁移和恢复 |
| 查询索引 | SQLite + FTS5，可从永久资料重建 | 单机查询、目录关联和全文检索无需独立数据库服务 |
| 运行记录 | 单独的 SQLite 运行库 | 持久化任务、重试和费用记录，不随检索索引重建清空 |
| 语义检索 | 预留接口，按召回效果启用现有 LanceDB 适配 | 不作为离线启动和 MVP 基本检索的前置条件 |
| 后台执行 | SQLite 持久化任务 + 有限并发 Python 子进程 | 防止 OCR、解析与网络调用阻塞阅读界面 |
| 打包 | Electron Forge + PyInstaller onedir | 将前端与本地引擎作为一个安装包交付，无需用户安装 Python |
| 测试 | pytest、Vitest、Playwright/Electron 冒烟、干净 Windows 安装验证 | 分别验证逻辑、界面、桌面联通及实际交付 |

MVP 不引入 Docker、Redis、Celery、PostgreSQL 或 Neo4j；不开发团队协作、云同步和全文写作代理。编辑笔记先采用 Markdown 文本编辑与预览，富文本编辑器后置。

版本管理：沿用现有锁文件进行兼容验证；新增依赖在实施时选择仍受支持的稳定版本并精确锁定，不在本文虚构“最新版本号”。Node 构建工具版本与 Electron 内置 Node 版本分别管理。锁定 Python、解析库、PDF.js worker 和 OCR 资源的版本与校验值。

## 2. 当前仓库基础与差距

以下为本次静态代码核对结果，不等同于完整功能验收。表中 `app/`、`frontend/` 均相对于 `旧项目-ResearchKB/`；`demo/` 相对于 `新项目-知拾/`。复用指后续审查并复制模块，不允许新项目跨目录导入旧源码或共享虚拟环境、配置及知识库。

| 位置 | 已有基础 | 对照 PRD 的处理 |
| --- | --- | --- |

| `app/repositories/file_store.py` | 原件与开放格式永久资料 | 继续作为资料事实来源，补原子写入、修订及崩溃恢复 |
| `app/repositories/sqlite_store.py` | SQLite/FTS5 派生索引 | 扩展为区块索引、多主题关系和修订号投影 |
| `app/jobs/queue.py` | SQLite 作业记录，同步执行 | 改为持久化异步作业和隔离 worker |
| `app/llm/` | Provider、缓存、预算、结构化输出与依据校验 | 复用接口，补覆盖率、摘要分类、取消与不确定费用状态 |
| `app/services/citation_service.py` | GB/T 7714、APA 模板 | 新增独立法学引注模板；现有两种样式不能视为《法学引注手册》实现 |
| `app/storage/migration.py` | FTS 优先 trigram，失败回退 unicode61 | 修正中文短词召回问题，不能将回退视为中文检索等价支持 |

当前 Git 中大量原有后端、前端和配置文件尚未纳入版本管理。开发启动阶段应先核对并建立可复现的基础提交，排除 `.env`、真实知识库、缓存与运行日志；不能只提交新桌面壳而遗漏运行依赖。

此前后端测试出现过本机 API Key 配置污染测试环境的问题。正式开发前修复测试隔离并建立全套基线；本次文档工作不声称该问题已解决。

## 3. 进程职责与通信

### 3.1 四个执行边界

| 部分 | 负责 | 不承担 |
| --- | --- | --- |
| React 渲染进程 | 文献列表、原文展示、笔记编辑、分类调整、进度与证据卡 | 直接访问磁盘、任意命令执行、长期保存 Key |
| Electron 主进程与 preload | 窗口、文件选择、受限 IPC、引擎启停、凭据保管、资源流转 | PDF/OCR 计算、模型业务判断、复杂同步文件读写 |
| Python 本地服务 | 业务命令、持久化、检索、分类策略、任务调度、Provider 调用 | 桌面 UI 控制、执行文档中的指令 |
| Python worker 子进程 | 解析、OCR、可取消的耗时处理 | 直接修改正式资料、直接持有数据库写连接 |

Electron 提供主进程、渲染进程和受限桥接机制；本方案利用这些边界隔离 UI 与文件能力。[Electron 进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)

### 3.2 通信选定方案

采用 **渲染进程 → 具名 IPC → Electron 主进程 → 已认证的本地 FastAPI**。Python 服务只监听 `127.0.0.1` 的系统分配端口，由主进程管理；不对局域网开放。

- preload 只暴露具名操作，如 `listSources`、`saveNote`、`updateTopics`、`startIngest`。不暴露通用 `exec`、任意路径读写或任意 URL 转发。
- 主进程校验 IPC 发起窗口、参数结构和大小，映射到固定的 API 路由。渲染进程不直接获得本地服务会话令牌。
- 主进程启动引擎前生成本次会话令牌，通过子进程私有标准输入管道传递；引擎完成端口绑定后，通过标准输出返回结构化 ready 消息。普通日志写 stderr，禁止打印令牌。
- HTTP 接口全部验证会话令牌，包含 health、原件读取和事件流。校验 Host，不开放任意 CORS；绑定 localhost 本身不能替代认证。
- 任务进度使用引擎事件流，由主进程转发到订阅窗口；携带 event_id、job_id，重连后查询任务快照补齐状态。
- 正式界面从注册的本地 `app://` 协议加载。PDF/图片从受控 `zhishi-asset://` 资源协议读取，主进程按 source_id 映射资源并向引擎附加认证；支持流式 Range 读取，不把整份大 PDF 经 IPC 编成 Base64。
- 外部网页默认交给系统浏览器；在应用内阅读的是提取并清洗后的内容，不加载网页原始脚本。

启用 `contextIsolation`、渲染器 sandbox，关闭 Node integration，不关闭 `webSecurity`；IPC 白名单和内容安全策略随安装包测试。以上是本产品处理不可信文献所需的实际边界。[Electron 安全建议](https://www.electronjs.org/docs/latest/tutorial/security)

### 3.3 生命周期

启动：单实例检查 → 打开知识库与写锁 → 启动打包后的引擎 → 验证 API/schema 兼容性 → 恢复未结束任务 → 显示可用工作台。启动失败展示诊断和重试入口，不能永久空白。

退出：先保存笔记、停止接受新作业，再取消/暂停运行任务，完成持久化后关闭引擎。主进程异常退出时，引擎通过控制管道断开或心跳失效终止；下次启动将遗留 running 作业转为 interrupted，不能同时启动多个写入者。

MVP 默认关闭应用即停止后台处理，不提供未经提示的长期后台驻留。重启引擎需限制次数并保留错误信息。

## 4. 存储、数据模型与一致性

### 4.1 数据职责

保留原项目“开放文件为永久资产，SQLite 为查询索引”的基础，避免本次桌面化同时引入一套相反的数据权威关系。

| 数据 | 权威保存位置 | 是否允许重建 |
| --- | --- | --- |
| 原始文件、网页快照、原始文字 | 知识库内原件目录，SHA-256 校验 | 不可从模型或索引重建 |
| 来源、摘要、主题归属、笔记、证据、回答 | 版本化 JSON/YAML/Markdown 文件 | 保留原记录；索引不得反向覆盖它们 |
| 列表投影、主题关联、FTS、向量 | `indexes/` | 可从永久资料重建；不触发新的云端请求 |
| 作业、费用预占、实际用量、请求状态 | 新增 `runtime/operations.sqlite` | 不能作为普通缓存删除；纳入备份 |
| API Key | 操作系统保护的应用凭据文件 | 不进入知识库、索引或导出包 |

知识库位于用户选择的数据目录，不能位于安装目录或应用升级会覆盖的位置。内部记录相对路径；首发不支持多个应用实例同时写同一知识库，也不支持同步盘并发编辑。

### 4.2 核心对象

| 对象 | 关键字段和约束 |
| --- | --- |
| Source | `id`、文件类型、标题、作者、原件路径/hash、来源 URL、采集时间、各处理阶段状态、schema_version、revision |
| Bibliography | 文献类型、类型化出版字段、每个字段的来源与确认状态；未知值为 null |
| ParseRevision / Block | 解析版本、区块 id、text/table/image、原文/整理文、定位、质量、覆盖范围、原始区块映射 |
| Summary | source_id、parse_revision、summary_id/version、mode（抽取式/模型/人工）、内容、evidence_ids、覆盖范围 |
| TopicAssignment | source_id、topic_ids、primary_topic_id、revision、确认状态、分类方法、摘要版本、理由 |
| ClassificationRun | 候选分数、主题依据、参照样本、规则/模型版本、建议状态；不直接覆盖人工决定 |
| Note | note_id、source_id、可选 block_id、Markdown、revision、创建与更新时间 |
| Evidence | source_id、parse_revision、block_id、原始摘录、范围、locator；摘要不是原文引语 |
| Answer | 问题、查询范围快照、证据快照、结构化论断、验证状态、模型与模板版本 |
| Job / Usage | job_id、阶段、状态、幂等键、attempt、输入/输出版本、费用预占与结算状态 |

沿用现有 ULID 作为永久 id。主题表与 SourceTopic 关系在 SQLite 中建立索引；每个 `(source_id, topic_id)` 唯一。主题赋值的权威版本与主主题放在同一记录中原子保存。主主题必须属于已选主题集合；未分类可为空。

### 4.3 写入与故障恢复

统一由 Python 服务执行持久化命令，worker 只返回暂存结果。新增对象和修订先写到同卷临时文件，校验后原子替换发布；不在原始文件上直接修改。版本文件先落盘，当前记录再引用新版本，使旧版本在中断时仍可读取。

每条修改命令带 operation_id 和 expected_revision。服务先检查修订号，将完整的新对象版本落盘，再发布当前版本指针，最后更新 SQLite 投影。并发冲突返回 409，由界面展示冲突；不会用最后到达的旧请求覆盖新笔记。

文件与 SQLite 不宣称是一个跨介质事务。永久资料已经提交但索引更新失败时，返回“已保存，索引待恢复”和操作编号；详情读最新文件，列表标识索引更新中。启动恢复比较修订号并补建投影。未被当前版本引用的暂存解析产物不参与检索，清理前核对引用。

单次分类修改将所有 topic_ids 和 primary_topic_id 一起发布，防止出现短暂的“主主题不在归属集合中”。重新解析先保存新证据与区块，最后切换 source 的当前 parse_revision；旧问答继续引用原快照并标注版本变化。

### 4.4 备份与迁移

导出包括原件、永久对象、修订信息、主题配置、运行库快照及清单校验值，不含 Key 和可重建缓存。导出时短暂停止提交形成固定修订清单，再复制不可变版本；运行库通过 SQLite Backup API 取快照，不能直接复制正在写入的数据库主文件。恢复到新目录，先验 hash、schema 和引用关系，再重建索引并切换。[SQLite 备份说明](https://www.sqlite.org/backup.html)

迁移前创建可恢复快照，保留 source_id、原件 hash 和旧主题。九个既有对应主题沿用稳定 id，人工智能主题只调整显示名；新增“其它”。旧“标准化法”“法学方法”不盲目全量映射到法律科技创新：保留 legacy_topic，标为待核对，依据摘要给出新建议。旧分类是否人工确认未知时按需保护，不当作已确认训练样本。

迁移具备 dry-run 报告、幂等执行、版本记录和失败回退；禁止直接操作用户原库来验证迁移脚本。前端三主题 DEMO 不作为真实数据迁移来源。

## 5. 收录、解析与阅读

### 5.1 统一摄入

入口接收文件、文字或 URL，先流式保存原件并计算 hash，再登记任务。相同 hash 提示已有文献；同一 URL 的不同时间快照保存为修订，不把不同正文合并覆盖。原件成功落盘后界面即显示“已存档”，解析与分析在后台继续。

初始限制建议：单文件 100 MB、PDF 1000 页；超过阈值仍可选择仅存档，不能静默截断并宣称完整解析。具体上限须根据实测调整，压缩格式另设置解压总量和单元格数量上限。

### 5.2 解析适配器

| 输入 | 实现基础 | 输出与限制 |
| --- | --- | --- |
| 文本 PDF | 复用 PyMuPDF 与现有 pdf_layout | 提取文本块、坐标、页与图片；复杂阅读顺序标记待核对 |
| 扫描 PDF/图片 | 先检测有无可用文字层；独立 OCRAdapter | 优先可选本地 OCR 包，未安装或质量不足时按授权调用 OCR/视觉 API；保留页图与识别框 |
| DOCX | python-docx + 必要的 OOXML 读取 | 段落/表格/图片，补脚注关系；无固定 Word 页码，不伪造分页 |
| XLSX | openpyxl | 工作表、单元格、合并范围、公式及缓存值；不执行宏或公式 |
| 网页 | HTTPX + trafilatura + HTML 清洗 | 保存原快照，输出清洁区块、来源与访问时间；复杂登录网页仅存链接 |
| 文字 | 编码识别与规则规范化 | 原始版本与整理版本并存，标题/列表/表格不随意拼接 |

PyMuPDF 是现有依赖，正式分发前确认开源/商业许可路径并记录决定；解析器接口允许替换，不能因为项目自身标记 MIT 就推定所有依赖都可按同一条件分发。[PyMuPDF 官方说明](https://pymupdf.readthedocs.io/en/latest/about.html)

本地 OCR 初步候选为可独立分发的中文识别引擎，选型须用扫描件样本比较质量、启动耗时、模型大小和许可；不把大型模型强塞进首次安装包。没有 OCR 能力时仍能存档和看图，显示待识别状态。

### 5.3 定位与全文质量

每个解析区块保存类型化 locator：PDF 使用从 0 开始的 page_index、独立的印刷页码、页面宽高/旋转及 bbox；网页使用快照 id 和区块锚点；Word 使用标题路径/段落；Excel 使用 sheet 和 A1 范围；图片使用图像 id 和区域框。

PDF.js 渲染坐标通过 viewport 变换与解析坐标转换，不能直接把 CSS 像素当 PDF 坐标。证据选中保存原文及前后文作为二次定位校验。页索引与印刷页码不能互相猜测。[PDF.js 官方介绍](https://mozilla.github.io/pdf.js/)

质量统计包括总页/成功页、空白页、待 OCR 页、失败区块、乱码比例和表格提取状态。只有正文覆盖符合规则时才提供“全文摘要”；部分解析仍可阅读，但摘要显示处理范围。OCR 结果独立于原文，并有核对状态。

### 5.4 阅读工作台

PDF 采用可见页懒加载，限制画布缓存；长文献列表和表格按窗口/分页渲染。Word 和网页使用统一的整理阅读组件，不追求逐像素复刻原版。图表保持独立区块，点击可放大并查看来源；Excel 显示缓存值及公式，不将其解释为重算结果。

原件、提炼观点和个人笔记分栏且有清晰标识。MVP 支持选中文字形成带位置的摘录笔记；任意框选、复杂跨页批注仍按 PRD 放在 P1。笔记采用显式保存或带保存状态的防抖保存，关闭前处理未提交内容，重启可恢复草稿。

## 6. 摘要与十大主题分类

### 6.1 稳定主题表

主题完整范围以 PRD 4.3.1 为准，配置文件与前后端类型共同生成，不在多个 UI 文件手写不同名单。

| 顺序 | 稳定 id | 名称 |
| --- | --- | --- |

### 6.2 摘要先于分类

无模型时先从标题层级、章节内容和句子权重生成抽取式摘要；保留原句与区块引用。有模型时按章节分块提炼，再合并中心命题、论据与限制。摘要携带解析版本及覆盖范围。不能继续使用“标题 + 前 6000 字”作为摘要分类的替代品。

分类输入由摘要、必要关键词、主题定义和少量已确认相似样本组成。第一阶段做规则和本地相似度评分；依据充分则自动提交未确认的建议归属，边界不明再调用已授权的模型。模型只允许输出十类稳定 id，结构校验失败进入待核对。

相似度实现 MVP 可采用摘要字符 n-gram/词项向量与余弦相似度；使用同一预处理版本。语义向量属于可替换增强，不能因未安装 embedding 模型就中断分类。主主题和附加主题阈值分别校准，每个附加主题必须给出摘要依据，不预设虚假的准确率。

### 6.3 多主题与人工优先

- 从九个具体主题中选择最相近的主主题；多个主题均有实质依据时形成 topic_ids 集合。
- 充分解析但与九类无关联才建议“其它”；不把缺失摘要、OCR 失败或不确定自动填为“其它”。
- 自动归类默认不混选“其它”和具体主题；人工选择出现冲突时明确提示再保存。
- 每次人工修改保存完整前后集合、revision 与原因，支持撤销。用户确认后锁定当前主题集合，包括用户明确移除的主题，防止重跑时悄悄补回。
- 新摘要生成新 ClassificationRun；如果已有人工确认，仅显示建议，不改当前归属。
- 相似样本仅取明确确认的记录；按原件 hash 和来源修订去重。同文献在多个主题下只是一条样本。
- 主题并集查询使用 DISTINCT source_id；交集查询要求匹配全部指定主题。总文献数按 id 计，主题数量之和可以更大。

## 7. 检索、精准问答与引注

### 7.1 中文全文检索

将索引粒度从整篇扩展到区块，保存 source_id、parse_revision、block_id、章节及可验证原文。MVP 使用 FTS5 的词项排名与主题/状态过滤；中文采用应用层分词加短词索引，索引和查询用同一版本的分词规则及法律术语词典。

现有 trigram 对不足三个字符的查询存在限制，不能直接保证“同意”“隐私”等短词召回。保留 trigram 作为较长子串通道时，短词必须走词项索引或受限的短词回退，并用 A/B 样本验证结果；不将 unicode61 原样回退当作完整中文分词。[SQLite FTS5 文档](https://www.sqlite.org/fts5.html)

引入向量检索时，先在指定文献范围内过滤，再与词项召回合并、去重和排序。记录 embedding provider、模型、维度与版本；切换模型必须重建对应向量，不混用旧维度。只有评估表明需要时才启用 reranker，不在初版堆叠多个模型。

### 7.2 问答流程

1. 固定本次主题/文献范围与资料版本，检索原文区块；个人笔记默认排除。
2. 无 Key 返回原文证据列表，有 Key 时把经校验的候选片段发送给模型，要求输出结构化论断与 evidence_ids。
3. 每个论断检查证据存在、版本、定位与引语匹配；规范化引语匹配须保留到 raw 的位置映射，不能只在整理文中匹配后伪称原始引文。
4. 区分“直接引语”“模型概括”“个人判断”。ID 或文字校验只能验证出处，不能证明语义蕴含；对概括另做支持性审查，无法确认时降级为原文摘录或依据不足。
5. 支持/反对/限制仅在证据确实存在时呈现，不能把没搜到反例写成不存在反例。点击证据打开对应版本和 locator。
6. 保存回答及证据快照。文献删除、来源修订或证据失效后，回答显示过期/待复核状态，不悄悄替换出处。

MVP 先完整返回并验证答案，再展示可引用结果。流式进度可以展示，但未通过验证的生成片段不得作为已核验回答复制导出。

### 7.3 法学引注

新增独立的法学引注模板引擎，按文献类型读取已核对字段；不依赖模型自由拼接引文，不把现有 GB/T 7714 或 APA 改名当作法学引注。

模板记录手册版本、规则编号/出处和修订号；期刊、专著、网页、法规、裁判分别定义必需字段与适用定位。DOI 是可选标识，不应沿用当前代码将所有论文缺 DOI 一概判为不完整的逻辑。

缺少字段返回 missing_fields 与草稿；具体页码未知时保留为空。独立引注先实现，“同上注”等全文上下文样式和 Word 插件不进入 MVP。第二版手册全文核验与黄金样例通过之前，不标记“完全符合《法学引注手册》”。

## 8. 作业、模型路由与凭据

### 8.1 作业模型

每个阶段独立记录 `queued/running/succeeded/failed/cancelled/interrupted/blocked`。处理步骤包括存档、本地解析、OCR、索引、摘要、分类；部分步骤可并行，但分类依赖可用摘要，不能在摘要还未形成时标为摘要分类完成。

幂等键包含 source_id、输入 hash/修订、任务类型、解析器/规则/模型/提示模板版本及 provider 标识；同一输入重试复用已完成结果，不重复生成资料。业务写入通过中央写入队列串行提交，解析初始并发建议 2、OCR 并发 1，实测后调整。

超时和取消向 worker 传递信号，必要时终止对应子进程；已存原件不删除。作业 lease 与心跳用于恢复，重启只恢复安全可重试阶段。

### 8.2 云端路由与预算

保留现有 Provider 接口，优先接通用户配置的兼容 API，OCR/视觉模型单独声明能力；不要假定任一聊天 API 都支持图片、JSON schema 或 embedding。连接测试说明是否发起收费请求。

调用前按用户授权策略、发送范围、单篇/每日预算检查并预占额度；完成后结算。缓存键包含库标识与内容 hash，不能跨知识库泄露材料。超时后服务商可能已计费，标记 usage_unknown 并保留预占，支持核对，不宣称绝不会重复收费；无服务商幂等支持时不盲目自动重发不确定请求。

无需云端的收录、检索、笔记与人工分类永远不依赖 Key。模型输出中的工具或系统指令视为文献内容，不获得执行权限。

### 8.3 Key 与网络

桌面端使用 Electron safeStorage 加密凭据，由主进程保存在应用私有配置目录；UI 仅在用户输入时短暂持有，提交后清空，不放入 localStorage。主进程按需通过私有管道将凭据交给引擎内存，运行结束释放。该机制保护静态存储，不声称能抵御同一登录用户下的恶意进程。[Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage)

用户主动配置的本地模型服务可使用回环地址；网页抓取器的 URL 与重定向不得访问回环、私网、链路本地和系统文件。两类网络策略分开实现。抓取逐次验证解析地址与实际连接目标，防止重定向及 DNS 重绑定绕过；URL、正文和日志不包含令牌。

## 9. 接口与模块组织

使用 Pydantic 模型生成 OpenAPI 与前端 TypeScript 类型。新增桌面接口使用 `/api/v1`；旧接口通过适配层逐步迁移，不能让前后端分别猜字段。读接口不隐式写分类或调用模型，需移除当前资料详情读取时触发分类的副作用。

| 接口/操作 | 合同要点 |
| --- | --- |
| POST /api/v1/ingest/file、text、url | 返回 source_id、job_id、原件是否已保存、当前阶段；支持幂等键 |
| GET /api/v1/sources | 分页、query、topic_ids、topic_mode=any/all、类型和状态；source 去重 |
| GET /api/v1/topics | 十类稳定 id、显示名、顺序、各主题文献数；系统视图独立 |
| PATCH /api/v1/sources/{id}/topics | 完整主题集合、可空主主题、expected_revision、人工确认；409 冲突 |
| GET /api/v1/sources/{id}/blocks、original | 指定版本、区块分页/定位；原件范围读取，校验 source_id |
| POST /api/v1/sources/{id}/analyze | 任务类型、输入版本、云端授权；只排队，不阻塞直到分析结束 |
| GET/POST/PATCH /api/v1/notes | source/locator 关联、Markdown、expected_revision；明确保存状态 |
| POST /api/v1/search、answers | 固定检索范围与版本；区分证据列表和经过验证的生成回答 |
| GET /api/v1/sources/{id}/citation | 样式版本、引证位置、草稿、缺项、字段来源 |
| GET /api/v1/jobs；POST /api/v1/jobs/{id}/cancel、retry | 状态快照、阶段、错误、恢复策略 |
| GET /api/v1/events | job/operation 事件，event_id 及可恢复订阅 |
| POST /api/v1/exports、imports/validate | 后台导出与先验证后恢复；返回任务而非长时间阻塞 |

错误统一包含 code、message、retryable、operation_id 和非敏感 details。引擎与 UI 使用能力清单进行协议握手；不兼容时停止写库并提供升级/恢复指引。

正式实施时在 `新项目-知拾/` 内新增 `desktop/` 存放 main、preload、IPC 合同和资源协议；建立独立的 `frontend/` 与 `app/`，从旧项目选择性复制经过验证的模块。在新 `app/` 下补充 notes、summaries、classification、reader、operations 等模块，不将所有逻辑塞进 `api/main.py`。新项目独立管理锁文件、环境与资料库，旧项目保留原有行为。现有 MCP/Zotero 集成保持可选，不作为首次打开依赖。

## 10. 打包、升级与交付

### 10.1 先验证打包，再扩展功能

第一个工程里程碑即完成 Electron 窗口、一个真实 API 调用和打包后的 Python 引擎启动。使用 PyInstaller onedir 将解释器、动态库、提示模板、迁移 SQL 和 schema 一并收集；将资源明确列入打包清单，不能依赖源码相对目录恰好存在。PyInstaller 打包需在目标平台构建并验证。[PyInstaller 工作方式](https://pyinstaller.org/en/stable/operating-mode.html)

Electron Forge 负责桌面应用打包与安装产物；先选定并验证 Windows 安装方式，Python 引擎置于资源目录外部可执行位置，不放进不可直接执行的归档内部。先提供安装包手动升级，再加入自动更新；不要为了上线 MVP 自建复杂更新平台。[Electron Forge](https://www.electronforge.io/)

### 10.2 分发与数据保留

- 安装包包含前端静态资源和 Python 引擎；用户无需安装 Node、Python、Git 或启动终端。
- 更新替换程序资源，不覆盖知识库、笔记和配置。数据库/schema 升级先备份，失败停止写入；旧程序不读取更高版本 schema。
- 外发版本签名，保存依赖许可清单和构建版本。程序、引擎、API schema、解析器与提示模板版本可在诊断页查看。
- OCR 模型如作为可选组件下载，应显示大小、来源和校验结果，下载失败不影响现有资料。
- 卸载默认保留用户资料；清除资料必须是单独、明确的用户操作。
- 不将生产密钥或个人资料打入安装包，也不默认上传错误报告或文献正文。

### 11.3 性能验收目标

基准暂定 Windows 11、16 GB 内存、SSD；以 1 万份文献、约 20 万文本区块作压力基线，首批真实数据用于校准。建议目标：暖启动工作台 5 秒内可操作，目录/元数据查询 P95 小于 300 ms，本地文本检索 P95 小于 1 秒；大型 PDF 首屏按需加载，后台处理时界面无持续超过 200 ms 的主线程阻塞。

上述为目标而非测量结果。OCR、模型响应和初次索引单独记录耗时，不用外部 API 延迟考核本地界面。记录空闲、阅读和批量处理内存峰值，基于实测设预算，不先承诺固定极小安装体积。

| Electron + Python 安装较重 | 先做真实安装验证，延迟载入 OCR/向量组件；按实测调整 |
| 中文多栏 PDF、扫描表格质量不稳定 | 原件永远可回看，质量/覆盖显式；不把重排结果替代原件 |
| 多主题过度归类 | 摘要与各主题的实质依据、单类/多类分别评估、人工保护 |
| 证据存在但无法支持答案 | 区分定位校验与语义支持性校验；不足时回退到原文 |
| 文件与索引写入中断 | 单写入者、不可变修订、原子发布、投影修复与故障注入测试 |
| 引注规则与投稿要求不同 | 固定手册和模板版本，保留可扩展样式；未核验规则不标完整 |
| 旧 11 类与新 10 类冲突 | 保留原值与记录，未知人工状态保护，摘要建议而非盲目覆盖 |
| 用户自配 API 协议不一致 | Provider 能力检测、结构验证和清楚的降级提示 |
